§1Problem statement

Glossmark builds only for Linux, and only inside CI's package job. The .deb and the AppImage it makes are kept for seven days as an Actions artifact, and nobody outside the repository can find them. Windows and macOS have no build at all. Export to PDF works only on Linux (D-20, D-4). There is no version scheme, no release and no way to update. The owner wants a free app that anyone on Linux, Windows or macOS can install from where they already look for software, and that stays current. There is no paid signing and no Apple Developer program (D-24). This is a planned improvement. Nothing is broken, but the viewer has no users until it ships.

Ideas covered: I-14 (packages for Linux, Windows and macOS). D-30 comes from the same conversation but belongs to S-1; it is queued as its own task (t-6723dbe0) and is outside this spec's plan.

Success criteria (measurable)

  • [ ] release_assets_missing == 0. Pushing a tag vX.Y.Z creates a GitHub Release whose assets include a .deb and an .AppImage (x86_64), an .msi and an NSIS -setup.exe (x64), a universal .dmg, and the updater's latest.json with a .sig per updatable bundle.
  • [ ] release_workflow_minutes <= 60, measured from the tag push to the published Release.
  • [ ] deb_package_mb <= 20 (unchanged). msi_mb <= 20 and dmg_mb <= 30, reported in the job summary like the .deb.
  • [ ] install_smoke_failures == 0. On each OS runner, the release workflow installs the bundle it built (the .deb with apt, the .msi with msiexec /qn, and the .dmg by copying the .app), launches it with a fixture file, and the process is still alive after 10 s.
  • [ ] channel_version_lag_hours <= 72 for winget, Homebrew tap, Snap and the apt repo: each channel serves the new tag within 72 h of the Release. Flathub's first submission is exempt, because Flathub reviews it by hand.
  • [ ] Channel installs, judged once by the owner on a clean machine and recorded in the evidence log: winget install nuncaeslupus.Glossmark, brew install --cask nuncaeslupus/tap/glossmark, flatpak install flathub io.github.nuncaeslupus.glossmark, snap install glossmark, and apt install glossmark after adding the repo. Each one opens a .md file by double-click.
  • [ ] Self-update, judged by the owner. An AppImage, an .msi install and a .dmg install of vX.Y.Z each offer vX.Y.Z+1 within one minute of start, install it and restart into it. An update whose signature fails verification is refused (unit test on the verify path).
  • [ ] export_pdf_pages on Windows and macOS equals the Linux page count ±1 for e2e/fixtures and the README fixture. The PDF is paginated (A4 or Letter pages), not one long page. Judged by the owner on one exported file per OS.
  • [ ] secrets_in_repo == 0. The update-signing key, the apt GPG key and the store and tap tokens live only in GitHub Actions secrets. The gitleaks / GitGuardian check stays green.

Impact dimensions

  • Data: none. The app keeps no data beyond its config file.
  • API contracts: two new IPC commands for the updater (check, install). The Export contract is unchanged, and it starts working on two more OSes.
  • Performance: the update check is one HTTPS GET to GitHub after start-up. It must not delay first paint (S-1's start-up gate).
  • User-facing: the app becomes installable everywhere. Unsigned builds warn once on Windows and macOS.
  • Operational: releasing becomes git tag vX.Y.Z && git push --tags. There are four secrets to rotate if leaked, and four outside listings to keep alive.
  • Risk of inaction: a finished viewer that nobody can install.

§3Options

▸Option A: Releases only (Conservative)

  • Description: one release.yml using tauri-apps/tauri-action builds the three OSes on a tag and attaches the bundles and latest.json to a GitHub Release. Channels are filed by hand when wanted.
  • Scope: release.yml, tauri.conf.json, the updater plugin, README.
  • Effort: Small
  • Tradeoffs: + one workflow and no outside accounts. − It covers D-24 and D-28 only. Users must find the GitHub page, and D-26 and D-27 stay undone.
  • Compatibility: additive.

▸Option B: Releases, then channels that repackage the released binaries (Recommended)

  • Description: Option A, plus a job per channel that runs after the Release is published and consumes its assets. The winget PR and the Homebrew tap bump take the .msi and .dmg URLs and hashes. The snap and the Flatpak repackage the .deb. The apt repo indexes the .deb and signs the index. Every OS is built once and shipped through every channel, so a channel can never ship a binary that the Release does not have.
  • Scope: Option A, plus snap/snapcraft.yaml, a Flatpak manifest in the Flathub repo, the tap repo, an apt-publish job, and Windows and macOS print_to_pdf.
  • Effort: Large, but each channel is a separate task and none blocks the others.
  • Tradeoffs: + all of D-24 to D-29 within one build. + A channel that breaks fails its own job and leaves the Release intact. − Four outside listings, with four secrets. − Flathub prefers builds from source, but it accepts a repackaged .deb for an open-source app with a public release; if a reviewer insists on source, that becomes a follow-up.
  • Compatibility: additive.

▸Option C: Build every channel from source

  • Description: the Flatpak builds from source with vendored cargo and npm sources, a Launchpad PPA builds the .deb, and the snap builds from source.
  • Scope: Option B, with three more build systems that each need offline dependency vendoring.
  • Effort: Large+
  • Tradeoffs: + the "purest" packaging for distro reviewers. − Three more ways for one release to differ from another. − PPA builds need every Rust and npm crate vendored. − Many times the maintenance, for no user-visible gain.
  • Compatibility: additive.

§4Recommendation

Option B. It is the only option that meets the owner's "fast way, then the rest that are free" (D-24) with one build per OS. Each channel is a thin repackaging step that the plan can split into separate tasks.

Order of work (for design):

  1. Release workflow and versioning. Semver tags vX.Y.Z, starting at v0.1.0. The version in tauri.conf.json and Cargo.toml must match the tag, or the workflow fails. Builds:
    • Linux on ubuntu-24.04, matching today's CI, so the .deb runs on Ubuntu 24.04 and newer.
    • Windows on windows-latest: .msi and NSIS.
    • macOS on macos-latest: a universal-apple-darwin .dmg, signed ad hoc (signingIdentity: "-") so Apple Silicon runs it.

The workflow publishes a draft Release, runs the install smoke jobs, and only then un-drafts it. 2. Updater (D-28). tauri-plugin-updater, with an endpoint at https://github.com/nuncaeslupus/glossmark/releases/latest/download/latest.json and the public key in tauri.conf.json. The private key and its password go in Actions secrets. The updater runs only where the app can replace itself (AppImage, the Windows installers, the macOS .app). It is off when FLATPAK_ID or SNAP is set, or when the binary sits under /usr (the .deb, whether installed from apt or by hand). 3. Export on Windows and macOS (D-29). - Windows: WebView2 ICoreWebView2_7::PrintToPdf with print settings, through with_webview. - macOS: WKWebView.printOperation(with:) with NSPrintInfo job disposition NSPrintSaveJob to the chosen URL. createPDF does not work here, because it makes one long page, not a paginated document.

The export must ship before the first Windows or macOS Release. 4. Channels (D-26, D-27), each its own task, in this order: 1. Homebrew tap: a cask with auto_updates true, plus caveats that explain "Open Anyway". 2. winget. 3. apt repo. 4. Snap. 5. Flathub, last, because its human review takes the longest. 5. SignPath (D-25): apply as soon as the first Release exists, since they review a public project. Signing is enabled in a later task once they approve. 6. README: an Install section per OS, with the unsigned-app steps.

Immediate next action: the owner reviews this spec in the reader. On approval, design writes arsenal/project/packaging/plan.md with the contracts (release workflow inputs and secrets, updater IPC, print_to_pdf per OS) and tasks gated on the success criteria above.

Open questions

  • D-28 says the updater is off "in builds for winget and Homebrew". Those channels install the same .msi and .dmg as the Release. Turning the updater off there would mean building and hosting a second Windows and macOS binary per release. The recommendation is to keep one binary with the updater on. winget tolerates self-updating apps. The cask declares auto_updates true, so brew upgrade leaves the app alone and the app updates itself. Snap, Flatpak and apt stay as D-28 says. If the owner agrees, this becomes D-31 and supersedes that part of D-28. If not, the plan doubles the Windows and macOS builds.
  • Unsigned on macOS. Since macOS 15, right-click › Open no longer bypasses Gatekeeper for an unsigned app. The user goes to System Settings › Privacy & Security › Open Anyway once. This is accepted by D-24, and the README and the cask caveats say it.
  • Linux arm64. It is not in D-24. The ubuntu-24.04-arm runner is free for public repositories, so arm64 could follow later. It is out of scope until asked for.
